# 灵犀 × 飞书多 Agent 任务协调模式 — 原始需求

> 本文档描述灵犀桌面助理在已具备飞书接入能力的基础上，需要新增的"任务消息协调模式"的原始需求。供 cursor + claude opus 4.6 实现参考。

---

## 一、背景

灵犀当前已具备的飞书接入能力：

- **P2P 单聊消息轮询获取**：定时拉取机器人收到的单聊消息
- **规则匹配**：按关键词/正则匹配消息，触发对应处理逻辑
- **群聊消息事件通知**：群里有消息时收到事件回调
- **艾特机器人消息事件通知**：群里有人 @ 机器人时收到事件

**新需求**：在上述能力之上，新增一种**可灵活配置的"任务消息协调模式"**，让灵犀能够：

1. 监听特定群/特定来源的告警或任务消息
2. 自动接单，在主消息下开话题（thread）
3. 在话题内用**流式卡片**展示调度者思考过程（不 @ 人）
4. 用**普通话题回复**艾特其他 agent / 机器人 / 真人，分派子任务
5. 持续监听话题内的回复，串联多 agent 上下文
6. LLM 判断任务是否完成
7. PATCH 更新主消息卡片状态（接单→排查→结案）
8. 结案

---

## 二、目标场景

### 场景一：客服反馈自动分派

```
客服在群里反馈：用户 uid xxx 反馈"买了会员用不了"
   ↓
灵犀机器人自动接单 → 主消息卡片状态=接单中
   ↓ 开话题
话题内：
   ├── 流式卡片：调度者分析（思考过程，不 @ 人）
   ├── 普通卡片回复：@支付中台agent 任务分派（含背景/期望输出）
   ├── 支付中台agent 回复
   ├── 流式卡片更新：收到支付侧结论
   ├── 普通卡片回复：@加冰替身 任务分派（带支付侧已知信息）
   ├── 加冰替身 回复
   ├── 流式卡片更新：根因 + 修复建议
   └── PATCH 主消息卡片：已结案
```

### 场景二：告警自动接单

```
监控系统在群里推送告警：wallet 日志报警 php-error
   ↓
灵犀机器人自动接单 → 主消息卡片状态=接单中
   ↓ 开话题，分派给对应 agent 排查
   ↓ 多 agent 在话题内协作
   ↓ 结案
```

### 场景三：人工调度

```
真人在群里 @ 灵犀机器人：帮我查一下 uid xxx 的订单
   ↓
灵犀机器人接单 → 主消息卡片 + 话题
   ↓ @ 对应 agent
   ↓ agent 回复
   ↓ 灵犀判断完成 → 结案
```

## 三、功能需求

### 3.1 任务模式配置

用户可以在灵犀侧灵活配置"任务模式"：

| 配置项 | 说明 | 示例 |
|---|---|---|
| `trigger_source` | 触发来源 | 群消息 / P2P / 告警 webhook |
| `trigger_match` | 触发匹配规则 | 关键词 / 正则 / 来源机器人 ID |
| `chat_id` | 监听的群 | `oc_xxx` |
| `dispatch_targets` | 可分派的 agent 列表 | `[{"name":"支付中台agent","open_id":"ou_xxx"},...]` |
| `card_template` | 主消息卡片模板 | 自定义 JSON |
| `thinking_card_template` | 话题内流式卡片模板 | 自定义 JSON |
| `task_card_template` | 任务分派卡片模板 | 自定义 JSON |
| `completion_strategy` | 完成判断策略 | LLM 判断 / 关键词匹配 / 手动确认 |
| `auto_close` | 是否自动结案 | true / false |

### 3.2 主消息生命周期

- **创建**：触发条件命中后，发送一张普通 interactive 卡片到群里
- **更新**：用 `PATCH /open-apis/im/v1/messages/{message_id}` 更新状态
  - 状态字段：`接单中 → 排查中 → 已结案`
  - 颜色字段：`orange → blue → green`
- **有效期**：14 天，全程只用一张卡片

### 3.3 话题管理

- **开话题**：主消息发出后，立即在下面发一条话题回复（流式卡片实体）
- **话题 ID**：用 `thread_id`（`omt_xxx`）作为任务状态机的 key
- **话题内消息类型**：
  - 流式卡片（1 张）：调度者思考展示，PUT 更新内容
  - 普通卡片回复（多条）：任务分派，含 @ 艾特
  - 文本/卡片回复（多条）：agent 的回复

### 3.4 流式卡片（调度者思考流）

- **创建**：`POST /open-apis/cardkit/v1/cards` 创建卡片实体，开启 `streaming_mode: true`
- **发送**：作为话题首条消息发出（`reply_in_thread: true`）
- **更新**：`PUT /open-apis/cardkit/v1/cards/{card_id}/elements/{element_id}/content`
  - 每次传**全量文本**（不是增量）
  - `sequence` 严格递增（1,2,3,...）
  - 频率建议 1-2 QPS，不要顶满 5 QPS 上限
- **内容**：纯展示，**不 @ 任何人**（流式 PUT 不触发 IM 事件，@ 了对方也感知不到）
- **超时**：流式模式会超时（错误码 200850），超时后需重新创建卡片实体

### 3.5 任务分派（普通话题回复卡片）

- **载体**：普通 interactive 卡片，作为话题回复发出（`reply_in_thread: true`）
- **艾特**：用 markdown 组件 `<at id=ou_xxx></at>`（plain_text 不渲染 @）
- **结构化模板**：
  ```
  @xxx 请协助排查

  **任务**：一句话描述任务

  **背景**：
  - 触发来源
  - 关键 ID（uid/gid/订单号等）
  - 时间

  **已知信息**（可选）：
  - 上游 agent 已确认的结论

  **期望输出**：
  - 具体要查什么
  - 要返回什么字段

  **上下文**：本话题内有完整排查过程，可按需拉取
  ```

### 3.6 话题回复监听

- **事件来源**：`im.message.received_v1` 事件订阅
- **归属判断**：事件体里的 `thread_id` 存在 → 话题内消息
- **状态机 key**：`thread_id`
- **发送者识别**：
  - `sender.sender_type == "app"` → 机器人回复
  - `sender.sender_type == "user"` → 真人回复
- **补偿机制**：服务重启或漏事件时，主动调用 `GET /open-apis/im/v1/messages?container_id_type=thread&container_id={thread_id}` 拉取完整话题历史

### 3.7 完成判断

每次收到话题回复后，调度者：

1. 拉取话题完整历史（或用本地缓存的事件流）
2. 喂给 LLM，prompt 类似：
   ```
   你是任务调度者。以下是话题 {thread_id} 的对话历史。
   判断任务是否已完成。
   - 完成：返回 {"done": true, "summary": "..."}
   - 未完成：返回 {"done": false, "next_action": "..."}
   - 需要 @ 谁：返回 {"mentions": ["ou_xxx"]}
   ```
3. 根据输出：
   - 未完成 + 需要 @ → 发新的任务分派卡片
   - 已完成 → PATCH 主消息到「已结案」+ 流式卡片收尾

**token 优化**：话题很长时做摘要，不要全量喂。

## 四、架构设计

### 4.1 模块划分

```
┌─────────────────────────────────────────────┐
│  灵犀飞书接入层（已存在）                    │
│  - P2P 轮询                                  │
│  - 群消息事件订阅                            │
│  - @ 机器人事件通知                          │
└──────────────┬──────────────────────────────┘
               │ 事件
               ▼
┌─────────────────────────────────────────────┐
│  任务协调模式（新增）                        │
│  ┌───────────────────────────────────────┐  │
│  │  触发匹配器                           │  │
│  │  - 按配置匹配群消息/P2P/告警          │  │
│  │  - 命中后创建任务实例                 │  │
│  └───────────────────────────────────────┘  │
│  ┌───────────────────────────────────────┐  │
│  │  任务状态机                           │  │
│  │  - key: thread_id                     │  │
│  │  - 状态: ALERT_RECEIVED →             │  │
│  │         ACK_SENT →                    │  │
│  │         TASK_DISPATCHED →             │  │
│  │         MONITORING →                  │  │
│  │         DONE                           │  │
│  └───────────────────────────────────────┘  │
│  ┌───────────────────────────────────────┐  │
│  │  卡片管理器                           │  │
│  │  - 主消息卡片创建 + PATCH 更新        │  │
│  │  - 流式卡片实体创建 + PUT 更新        │  │
│  │  - 任务分派卡片发送                   │  │
│  └───────────────────────────────────────┘  │
│  ┌───────────────────────────────────────┐  │
│  │  话题监听器                           │  │
│  │  - 按 thread_id 归属事件              │  │
│  │  - 主动拉取历史做补偿                 │  │
│  │  - 调用 LLM 判断完成                  │  │
│  └───────────────────────────────────────┘  │
└─────────────────────────────────────────────┘
```

### 4.2 数据结构

```typescript
interface TaskInstance {
  thread_id: string;              // 话题 ID，状态机 key
  root_message_id: string;        // 主消息 ID，用于 PATCH
  streaming_card_id?: string;     // 流式卡片实体 ID
  streaming_element_id?: string;  // 流式元素 ID
  streaming_sequence: number;     // 当前 sequence
  status: 'ALERT_RECEIVED' | 'ACK_SENT' | 'TASK_DISPATCHED' | 'MONITORING' | 'DONE';
  trigger_source: string;         // 触发来源
  trigger_content: string;        // 触发原文
  dispatch_history: Array<{       // 分派历史
    message_id: string;
    target_open_id: string;
    target_name: string;
    task: string;
    timestamp: number;
    replied: boolean;
    reply_content?: string;
  }>;
  created_at: number;
  updated_at: number;
}
```

### 4.3 配置文件示例

```yaml
task_modes:
  - name: "客服反馈自动分派"
    enabled: true
    trigger:
      source: "group_message"
      chat_id: "oc_5e1ca8976e721554ea7571eb2597097a"
      match:
        type: "keyword"
        keywords: ["客服反馈", "用户反馈", "买了会员"]
    dispatch_targets:
      - name: "支付中台agent"
        open_id: "ou_61f1d08c6aa0fe1532acc624516415f8"
      - name: "加冰替身"
        open_id: "ou_357a7e3776fa28f608bc9fefc1e15057"
    cards:
      main_card_template: "./templates/main_card.json"
      thinking_card_template: "./templates/thinking_card.json"
      task_card_template: "./templates/task_card.json"
    completion:
      strategy: "llm"
      llm_prompt: "./prompts/completion_judge.txt"
      auto_close: true
```

## 五、关键约束（必须遵守）

1. **流式卡片 PUT 不触发 IM 事件** — 不能用它来 @ 人，agent 感知不到
2. **普通话题回复才触发事件** — 任务分派必须用普通 interactive 卡片回复
3. **主消息卡片全程只用一张** — 用 PATCH 更新，不要重复创建
4. **流式卡片 sequence 严格递增** — 不能跳号、不能重复
5. **流式卡片会超时** — 错误码 200850，超时后重新创建实体
6. **卡片实体有效期 14 天** — 过期需重新创建
7. **JSON 2.0 的 update_multi 必须为 true** — 设 false 报 300302
8. **schema 必须显式声明 "2.0"** — 不声明默认 1.0，不支持流式
9. **bot 必须在群里** — 发消息、回复、@ 人都要求 bot 是群成员
10. **事件要做幂等** — 飞书会重试，用 message_id 去重
11. **tenant_access_token 2 小时过期** — 需要定时刷新

## 六、交付物

1. **任务协调模式核心模块**：触发匹配器 + 状态机 + 卡片管理器 + 话题监听器
2. **配置文件 schema**：YAML/JSON 格式的任务模式配置
3. **卡片模板**：主消息卡片 / 流式卡片 / 任务分派卡片三套模板
4. **LLM 判断 prompt**：完成判断 + 下一步分派建议
5. **补偿机制**：服务重启后能拉取未结案的话题继续推进
6. **日志和可观测**：每个任务实例的完整生命周期日志

---

## 七、验收标准

- [ ] 配置一个任务模式后，触发条件命中能自动开话题、发卡片
- [ ] 流式卡片能多次更新（打字机效果）
- [ ] 任务分派卡片能正确 @ 人，被 @ 的 agent 能收到事件
- [ ] agent 回复后，调度者能收到事件并更新流式卡片
- [ ] LLM 判断完成后能自动 PATCH 主消息到「已结案」
- [ ] 服务重启后能恢复未结案的任务
- [ ] 多个任务并行不串话（按 thread_id 隔离）
