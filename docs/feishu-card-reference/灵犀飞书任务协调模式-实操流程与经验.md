# 灵犀 × 飞书多 Agent 任务协调模式 — 实操流程与踩坑经验

> 本文档基于灵犀桌面助理实际跑通"客服反馈｜买了会员用不了"全流程的实操记录，包含所有验证过的 API 调用、踩坑、最终架构。供 cursor + claude opus 4.6 实现参考。

---

## 一、最终架构（双卡片模式）

经过多次迭代，最终跑通的架构是**双卡片模式**：

```
群主消息（普通 interactive 卡片，1 张）
├── PATCH 更新：接单中 → 排查中 → 已结案（header 模板颜色 orange→blue→green）
│
└── 话题（thread）
    ├── 流式卡片（1 张，调度者思考展示，不 @ 人）
    │   └── PUT cardkit 更新：分析 → 进展 → 根因 → 结案
    │
    ├── 普通卡片回复 1：@agentA 任务分派（含背景/期望输出/上下文）
    ├── 文本回复：agentA 的回复
    ├── 普通卡片回复 2：@agentB 任务分派（带 agentA 的已知信息）
    ├── 文本回复：agentB 的回复
    └── ... （按需继续）
```

### 核心原则

1. **主消息用普通 interactive 卡片 + PATCH 更新** — 不用流式卡片（流式 PUT 不触发事件）
2. **话题内流式卡片只做纯展示，不 @ 人** — 调度者思考过程
3. **真正艾特 agent 用普通话题回复卡片** — 这才会触发 `im.message.received_v1` 事件
4. **任务分派卡片结构化** — 任务/背景/已知信息/期望输出/上下文

### 为什么这样设计（关键洞察）

**流式卡片的 PUT 更新（`PUT /cardkit/v1/cards/{card_id}/elements/{element_id}/content`）不产生新的 message_id，不触发 `im.message.received_v1` 事件。**

也就是说，如果在流式卡片里写 `<at id=ou_xxx>`：
- 卡片渲染上确实会显示 @ 了人
- 但被 @ 的 agent **完全感知不到**（没收到事件）
- 所以 @ 是无效的

**必须用普通话题回复（`POST /im/v1/messages/{message_id}/reply` + `reply_in_thread=true`）来 @ 人，这条消息才会触发事件，agent 才能收到。**

## 二、完整实操流程（以"客服反馈"场景为例）

### 场景设定

- 群：`oc_5e1ca8976e721554ea7571eb2597097a`
- 用户反馈：买了会员用不了
- uid: 1275554101 / gid: 92785362
- 艾特对象：
  - 支付中台agent：`ou_61f1d08c6aa0fe1532acc624516415f8`
  - 加冰替身：`ou_357a7e3776fa28f608bc9fefc1e15057`

### Step 1：发送主消息卡片（普通 interactive）

**接口**：`POST /open-apis/im/v1/messages`

**关键点**：
- `msg_type: "interactive"`
- `content` 是**转义后的 JSON 字符串**（不是 JSON 对象）
- 卡片 JSON 用 `schema: "2.0"`
- 主消息卡片**不开** `streaming_mode`（用 PATCH 更新，不用流式）

**卡片 JSON 结构**：
```json
{
  "schema": "2.0",
  "config": {"update_multi": true},
  "header": {
    "title": {"tag": "plain_text", "content": "客服反馈｜买了会员用不了"},
    "subtitle": {"tag": "plain_text", "content": "uid 1275554101 / gid 92785362"},
    "template": "orange",
    "text_tag_list": [
      {
        "tag": "text_tag",
        "element_id": "status_tag",
        "text": {"tag": "plain_text", "content": "接单中"},
        "color": "orange"
      }
    ]
  },
  "body": {
    "elements": [
      {
        "tag": "markdown",
        "element_id": "summary_md",
        "content": "**用户反馈**：买了会员用不了\n\n**初步信息**：\n- uid：1275554101\n- gid：92785362\n\n**当前状态**：调度者已接单，正在分派排查"
      },
      {"tag": "hr", "element_id": "hr_1"},
      {
        "tag": "markdown",
        "element_id": "status_md",
        "content": "**进展**：\n- ⏳ 调度者分析中\n- ⏳ 待分派：支付中台、会员中台"
      }
    ]
  }
}
```

**调用命令（lark-cli）**：
```bash
lark-cli im +messages-send \
  --as bot \
  --chat-id oc_5e1ca8976e721554ea7571eb2597097a \
  --msg-type interactive \
  --content '<上面卡片 JSON>'
```

**返回**：`message_id: om_x100b6b554a2fa498b292dac23f7d853`（主消息 ID，后续 PATCH 用）

### Step 2：创建流式卡片实体

**接口**：`POST /open-apis/cardkit/v1/cards`

**关键点**：
- 请求体：`{"type": "card_json", "data": "<转义后的卡片 JSON 字符串>"}`
- `data` 字段是**字符串**，需要把卡片 JSON `json.dumps()` 后传入
- 卡片 JSON 必须 `schema: "2.0"`
- `streaming_mode: true`
- `update_multi: true`（2.0 必须）
- 要流式更新的元素**必须带 element_id**
- **必须用 markdown 组件**（`tag: "markdown"`）才能渲染 @（虽然流式卡片不 @ 人，但 markdown 比 plain_text 灵活）

**卡片 JSON 结构**：
```json
{
  "schema": "2.0",
  "config": {
    "streaming_mode": true,
    "update_multi": true,
    "summary": {"content": "调度者分析中"},
    "streaming_config": {
      "print_frequency_ms": {"default": 50},
      "print_step": {"default": 2},
      "print_strategy": "fast"
    }
  },
  "header": {
    "title": {"tag": "plain_text", "content": "调度者思考流"},
    "template": "blue"
  },
  "body": {
    "elements": [
      {
        "tag": "markdown",
        "element_id": "stream_md_01",
        "content": ""
      }
    ]
  }
}
```

**调用命令**：
```bash
# 先把请求体写到文件
cat > /tmp/create_card_req.json << 'EOF'
{"type":"card_json","data":"{转义后的卡片JSON}"}
EOF

# 调用（lark-cli api 的 --data 不支持绝对路径，要用相对路径）
cd /tmp && lark-cli api POST /open-apis/cardkit/v1/cards \
  --as bot \
  --data @create_card_req.json
```

**返回**：`card_id: 7657826311263865828`

**踩坑**：
- ❌ 用 `--as user` 会报 `99991668 user access token not support`，必须 `--as bot`
- ❌ `--data @/tmp/xxx.json` 报"invalid file path"，必须 `cd /tmp` 后用相对路径 `@xxx.json`

### Step 3：把流式卡片作为话题回复发出去

**接口**：`POST /open-apis/im/v1/messages/{message_id}/reply`

**关键点**：
- `message_id` 是主消息 ID（Step 1 返回的）
- `reply_in_thread: true` 让回复进入话题流（开启话题）
- `msg_type: "interactive"`
- `content` 格式**必须是** `{"type":"card","data":{"card_id":"..."}}`
  - ❌ 不是 `{"card_id":"..."}`（报 230099/200621 卡片 JSON 解析错误）

**请求体**：
```json
{
  "content": "{\"type\":\"card\",\"data\":{\"card_id\":\"7657826311263865828\"}}",
  "msg_type": "interactive",
  "reply_in_thread": true
}
```

**调用命令**：
```bash
cd /tmp && lark-cli api POST /open-apis/im/v1/messages/om_x100b6b554a2fa498b292dac23f7d853/reply \
  --as bot \
  --data @thread_card_msg.json
```

**返回**：
- `message_id: om_x100b6b55491474a4b242204bca12345`（话题内卡片消息 ID）
- `thread_id: omt_19239887048c9c85`（话题 ID，状态机 key）
- `root_id: om_x100b6b554a2fa498b292dac23f7d853`（= 主消息 ID）

### Step 4：流式更新调度者思考流（多次 PUT，不 @ 人）

**接口**：`PUT /open-apis/cardkit/v1/cards/{card_id}/elements/{element_id}/content`

**关键点**：
- 每次传**全量文本**（不是增量），新内容在旧内容末尾以打字机效果输出
- `sequence` 必须**严格递增**（1, 2, 3, ...），不递增报 300317
- 频率限制：1000 次/分钟、50 次/秒；单卡片 5 QPS
- 建议频率 1-2 QPS，不要顶满 5 QPS
- 流式模式超时会自动关闭（错误码 200850），需重新创建卡片实体

**第 1 次更新**：
```json
{
  "content": "收到客服反馈：用户反馈「买了会员用不了」。\n\n正在分析初步信息：\n- uid: 1275554101\n- gid: 92785362\n\n",
  "sequence": 1
}
```

**第 2 次更新**：
```json
{
  "content": "收到客服反馈：用户反馈「买了会员用不了」。\n\n正在分析初步信息：\n- uid: 1275554101\n- gid: 92785362\n\n**初步判断**：gid 是 92785362，疑似团队子账号，可能是席位未分配。需要先确认支付侧订单是否正常，再查会员侧权益是否下发。\n\n**分派计划**：\n1. 先 @ 支付中台agent → 查订单/合约状态\n2. 再 @ 加冰替身 → 查会员时长/席位状态",
  "sequence": 2
}
```

**调用命令**：
```bash
cd /tmp && lark-cli api PUT /open-apis/cardkit/v1/cards/7657826311263865828/elements/stream_md_01/content \
  --as bot \
  --data @seq1.json
```

### Step 5：发送任务分派卡片（普通话题回复，艾特支付中台agent）

**接口**：`POST /open-apis/im/v1/messages/{message_id}/reply`

**关键点**：
- `message_id` 还是主消息 ID
- `reply_in_thread: true`（话题内回复）
- `msg_type: "interactive"`
- 卡片 JSON **直接内联**在 content 里（不是 card_id 引用）
- **必须用 markdown 组件**写 `<at id=ou_xxx></at>`，plain_text 不渲染 @
- 任务卡片**结构化**：任务/背景/期望输出/上下文

**卡片 JSON 结构**：
```json
{
  "schema": "2.0",
  "config": {"update_multi": true},
  "header": {
    "title": {"tag": "plain_text", "content": "任务分派｜支付侧订单核查"},
    "template": "blue"
  },
  "body": {
    "elements": [
      {
        "tag": "markdown",
        "content": "<at id=ou_61f1d08c6aa0fe1532acc624516415f8></at> 请协助排查\n\n**任务**：确认 uid 1275554101 的订单和合约状态\n\n**背景**：\n- 用户反馈「买了会员用不了」\n- uid: 1275554101 / gid: 92785362\n- 反馈时间: 2026-07-02\n- 初步怀疑 gid 为团队子账号，席位未分配\n\n**期望输出**：\n- 最近一笔订单号、金额、状态\n- 合约状态（生效中/已取消）\n- 支付是否成功到账\n\n**上下文**：本话题内有完整排查过程，可按需拉取"
      }
    ]
  }
}
```

**调用命令**：
```bash
lark-cli im +messages-reply \
  --as bot \
  --message-id om_x100b6b554a2fa498b292dac23f7d853 \
  --reply-in-thread \
  --msg-type interactive \
  --content '<上面卡片 JSON>'
```

**返回**：`message_id: om_x100b6b55425874b0b2032b8dca7d247`

**关键**：这条消息**会**触发 `im.message.received_v1` 事件，被 @ 的支付中台agent 能收到。

### Step 6：模拟支付中台agent 回复（普通文本话题回复）

**调用命令**：

### Step 7：PATCH 更新主消息卡片状态（接单中 → 排查中）

**接口**：`PATCH /open-apis/im/v1/messages/{message_id}`

**关键点**：
- `message_id` 是主消息 ID
- 请求体格式：`{"msg_type": "interactive", "content": "<转义后的卡片 JSON 字符strings>"}`
- ❌ **不能直接传卡片 JSON**（报 99992402 field validation failed）
- ✅ 必须用 `msg_type` + `content` 包裹，content 是转义后的字符串
- 同张卡片有效期 14 天，5 QPS

**请求体**：
```json
{
  "msg_type": "interactive",
  "content": "{\"schema\":\"2.0\",\"config\":{\"update_multi\":true},\"header\":{\"title\":{...},\"template\":\"blue\",\"text_tag_list\":[{\"tag\":\"text_tag\",\"element_id\":\"status_tag\",\"text\":{\"tag\":\"plain_text\",\"content\":\"排查中\"},\"color\":\"blue\"}]},\"body\":{\"elements\":[...]}}"
}
```

**变更点**（相比 Step 1）：
- `header.template`: `orange` → `blue`
- `text_tag_list[0].text.content`: `接单中` → `排查中`
- `text_tag_list[0].color`: `orange` → `blue`
- `body.elements` 里 `status_md` 的内容更新为最新进展

**调用命令**：
```bash
cd /tmp && lark-cli api PATCH /open-apis/im/v1/messages/om_x100b6b554a2fa498b292dac23f7d853 \
  --as bot \
  --data @main_patch_req.json
```

## 三、所有踩坑记录

### 坑 1：card_id 引用语法

- ❌ `{"card_id":"..."}` → 报 230099 / 200621 "parse card json err"
- ✅ `{"type":"card","data":{"card_id":"..."}}`

### 坑 2：流式更新 @ 人必须用 markdown 组件

- ❌ `plain_text` 组件会把 `<at id=...>` 当字面文本显示
- ✅ `tag: "markdown"` 才能渲染 `<at>` 标签
- **但是**：流式卡片本来就不该 @ 人（不触发事件），这条只在任务分派卡片里有用

### 坑 3：卡片 vs 普通消息的 @ 语法不同

- 卡片内：`<at id=ou_xxx></at>`（`id`）
- 普通文本消息：`<at user_id="ou_xxx">名字</at>`（`user_id`）

### 坑 4：流式更新 sequence 必须严格递增

- 不能跳号、不能重复，否则报 300317

### 坑 5：流式模式会超时

- 错误码 200850，超时后需重新创建卡片实体（不能复用旧 card_id）

### 坑 6：卡片实体有效期 14 天

- 过期后 200750，需重新创建

### 坑 7：JSON 2.0 的 update_multi 必须为 true

- 设 false 报 300302

### 坑 8：schema 必须显式声明 "2.0"

- 不声明默认 1.0，不支持流式更新

### 坑 9：bot 必须在群里

- 发消息、回复话题、@ 人都要求 bot 是群成员

### 坑 10：PATCH 主消息卡片的请求体格式

- ❌ 直接传卡片 JSON → 报 99992402 field validation failed
- ✅ 必须用 `{"msg_type": "interactive", "content": "<转义后的卡片 JSON 字符串>"}` 包裹

### 坑 11：lark-cli api 的 --data 文件路径

- ❌ `--data @/tmp/xxx.json`（绝对路径）→ 报 "invalid file path"
- ✅ `cd /tmp && lark-cli api ... --data @xxx.json`（相对路径）

### 坑 12：创建卡片实体的认证身份

- ❌ `--as user` → 报 99991668 "user access token not support"
- ✅ `--as bot`

### 坑 13：机器人之间互相 @ 触发事件

- 前提：各机器人对应的应用都配了事件订阅 + `im.message.received_v1` scope + 在群里
- 否则 @ 了也收不到事件

### 坑 14：流式卡片 PUT 不触发 IM 事件（最关键）

- `PUT /cardkit/v1/cards/{card_id}/elements/{element_id}/content` 不产生新 message_id
- 不触发 `im.message.received_v1` 事件
- 所以**流式卡片里 @ 人是无效的**，agent 感知不到
- **必须用普通话题回复来 @ 人**

## 四、关键 API 清单

| 用途 | 方法 | 路径 | 备注 |
|---|---|---|---|
| 发主消息 | POST | `/open-apis/im/v1/messages` | msg_type=interactive |
| 话题回复 | POST | `/open-apis/im/v1/messages/{message_id}/reply` | reply_in_thread=true 开话题 |

## 七、MVP 实现建议（分阶段）

## 八、关键决策回顾

### 决策 1：主消息用普通卡片还是流式卡片？

**选普通卡片 + PATCH**。原因：
- 流式卡片 PUT 不触发事件，主消息不需要触发事件，但需要可更新
- PATCH 更新稳定，14 天有效期，5 QPS 够用
- 流式卡片有超时问题，不适合做主消息

### 决策 2：话题首条消息用什么？

**用流式卡片**。原因：
- 调度者思考过程需要打字机效果展示
- 流式卡片适合"渐进展示思考"
- 不 @ 人，所以不触发事件没关系

### 决策 3：任务分派用什么载体？

**普通话题回复卡片**。原因：
- 必须触发事件，agent 才能收到
- 卡片比文本更结构化，能承载任务/背景/期望输出
- markdown 组件支持 @ 渲染

### 决策 4：任务卡片里带多少背景？

**带完整背景 + 已知信息**。原因：
- agent 一眼拿到上下文，不用翻话题历史
- 多 agent 串联时，下游 agent 能看到上游结论
- "上下文：本话题内有完整排查过程" 兜底
